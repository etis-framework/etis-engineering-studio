# v0.18.2 — Review Workflow Reliability and Conversation Usability

**Status:** release candidate, **not deployed or published by this document**. Record acceptance only from verified evidence.

## User-visible changes

1. Start-another-review entry points use the established transition workflow; multiple Open sessions are retained and Finished sessions remain read-only. An initial-review top-button state defect was corrected and browser-retested locally.
2. Standard/Expanded conversation views, bounded internal scrolling, guidance for earlier turns, and draft-preserving navigation improve longer reviews and responsive layouts.
3. Finding status explanations separate discussion, evidence challenge, recorded disposition, and actual verified engineering work; frozen snapshot boundaries are preserved across rooms.
4. Evidence Room offers repository-relative artifact lookup in its **saved** snapshot, and preparation for a separate focused review. Unavailable saved evidence is not proof that a file is absent from GitHub.
5. Existing instructor/student authorization, evaluation authority, and evidence-governance boundaries are unchanged. No database migration or authority handoff is claimed.

## Local acceptance evidence (reported, pending release-independent confirmation)

- Full local Python pytest suite reported with zero failures and two skips; a later button-state correction was retested and reported passing.
- JavaScript workflow war games and focused tests passed on an earlier integrated candidate.
- Local synthetic browser trials exercised review transitions, conversation layout, keyboard access, and tablet-sized layout; these are not authenticated production acceptance.
- Six bounded live A2/A3 AI responses were independently judged technically defensible. A planning-oracle alternate architecture change trigger was adjudicated as valid; it does not change production model behavior.

## Final gates required before publication

1. Confirm clean feature branch, exact HEAD and cumulative diff; run `git diff --check`, full pytest and offline JavaScript checks against the **final** versioned commit. Review dependencies and CI/security results.
2. Validate student UX in a real browser, including multiple Open reviews, finished history, initial top-button action, drafts, source inspection, frozen/newer snapshot mismatch, keyboard and tablet widths. Conduct a human accessibility assessment; do not equate emulator checks with physical device or screen-reader acceptance.
3. Open feature PR into `main`, obtain review and green protected CI, merge, and record **exact merged SHA**.
4. Deploy only the accepted merged SHA using approved GitHub Actions production workflow. Explicitly select `reasoning_validation_mode=shadow` and `review_planning_mode=shadow` unless documented approval supersedes that policy; do not rely on legacy defaults.
5. Verify `/health` is 0.18.2 and `/ready` is healthy, application revision/image equals expected SHA, migration posture is safe, secrets/authorization boundaries remain correct, and operational telemetry is normal.
6. Run authenticated student/instructor smoke tests in Azure, with original and newer frozen evidence, multiple reviews, Finish read-only behavior, and real artifact availability. Record rollback artifact/revision and operator acceptance.
7. Reconcile documentation/manual edition before publication, then tag and publish only the deployed and accepted source commit.
